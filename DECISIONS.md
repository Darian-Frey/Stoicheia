# Decisions

Append-only log of significant design decisions.
Each entry: D-NNN, with Decided and Recorded dates (ISO 8601), status, context, alternatives, decision, consequences, and reversal conditions.
Status vocabulary: Proposed | Accepted | Superseded by D-NNN | Deprecated.

### D-001 Plain HTML, vanilla JS and SVG; no build step; GitHub Pages from `docs/`
**Decided:** 2026-10-27
**Recorded:** 2026-10-29
**Status:** Accepted
**Authors:** Shane Hartley (with Claude, scaffolding discussion 2026-10-27)
**Related:** F-001, F-015, AV-006, ARCHITECTURE.md §Key invariants

**Context.** The site needs to be hostable for free, pick-up-able after months away, and hackable in a text editor. The author's prior GitHub Pages project (Archive-19) used the same approach successfully.

**Options.**
- **A. Static HTML + ES modules + SVG, no tooling.** Zero install, zero rot from dependency churn. Chosen.
- **B. A bundler (Vite) with a framework.** Hot reload and components, but a toolchain to maintain and a `node_modules` to revive in a year. Rejected.
- **C. Canvas instead of SVG.** Faster for thousands of objects, but Euclid's figures have tens; SVG gives free hit-testing, CSS theming and accessibility. Rejected.

**Decision.** Option A. Everything in `docs/` is served verbatim; author-side scripts live in `tools/` and are never required to run the site.

**Consequences.**
- Serving locally is one command.
- No TypeScript; kernel contracts are documented in SPEC.md and enforced by the linter instead.
- Any third-party library would have to be vendored into `docs/`; none is planned.

**Reversal conditions.** Revisit if (a) a feature genuinely needs a build (e.g. generating 48 miniatures at commit time becomes too slow to do at page load), or (b) the project grows beyond Book I and shared components become unmanageable without a framework.

### D-002 Instrument visual direction
**Decided:** 2026-10-29
**Recorded:** 2026-10-29
**Status:** Accepted
**Authors:** Shane Hartley (mock-ups by Claude, 2026-10-27)
**Related:** F-005, F-006, F-015

**Context.** Three layouts were mocked up for Proposition I.1 on a design canvas: Codex (cream manuscript, two-column, everything visible), Instrument (dark cassette-futurism, mono type, readout panel, step-through transport), Notebook (white single column, step cards).

**Options.**
- **A. Codex.** Closest to reading the book; no interaction affordance beyond drag. Rejected.
- **B. Instrument.** Treats each proposition as an instrument you operate: readout, transport, gridded figure. Fits the author's existing cassette-futurism family. Chosen.
- **C. Notebook.** Most phone-friendly; least distinctive. Rejected.

**Decision.** Option B. Dark ground `#15171A`, panel `#1E2125`, amber accent `#E8B86D`, teal construction lines `#5FA8A3`, IBM Plex Mono body, Barlow Condensed display. Tokens in SPEC.md §Theme tokens.

**Consequences.**
- The step-through stepper is a Must feature (F-005), not optional.
- Phone layout (F-014) needs explicit work since the mock-up is desktop-first.
- A Codex theme remains a candidate feature; tokens are kept in CSS custom properties so a second theme is a file, not a rewrite.

**Reversal conditions.** Revisit if the dark theme proves hard to read for long proofs (I.44–I.47 are long) or if a second audience (teaching) asks for a print-friendly default.

### D-003 Propositions are data files, not hand-written pages
**Decided:** 2026-10-27
**Recorded:** 2026-10-29
**Status:** Accepted
**Authors:** Shane Hartley (with Claude)
**Related:** F-008, F-012, SPEC.md §Proposition data, AV-004

**Context.** Forty-eight propositions share one layout. Hand-writing 48 HTML pages would duplicate the shell and make theme or kernel changes a 48-file edit.

**Options.**
- **A. One `prop.html` shell + one data module per proposition.** Chosen.
- **B. 48 static pages generated by a script.** Needs a build step (contradicts D-001).
- **C. 48 hand-written pages.** Rejected: unmaintainable.

**Decision.** Option A. `prop.html?p=NN` loads `data/props/NN.js`. The data module is the single source of truth for statement, construction, proof, claims and dependencies; the dependency graph (F-012) and the linter are derived from it.

**Consequences.**
- Adding a proposition is one new file.
- The data schema (SPEC.md) is load-bearing and must be versioned carefully.
- Query-string routing means GitHub Pages needs no rewrite rules.

**Reversal conditions.** Revisit if query-string URLs become a problem for sharing or indexing (pretty URLs would need either a build step or 48 stub pages).

### D-004 Heath's translation as the proof text
**Decided:** 2026-10-29
**Recorded:** 2026-10-29
**Status:** Accepted
**Authors:** Shane Hartley
**Related:** F-007, AV-004, ARCHITECTURE.md §Key invariants

**Context.** The proof text needs to be accurate, citable, and free to republish.

**Options.**
- **A. Heath (1908), public domain.** Standard scholarly English text; every modern commentary keys to it. Chosen.
- **B. A modern paraphrase written for the site.** Friendlier, but invents a text that then has to be defended. Rejected.
- **C. Fitzpatrick's Greek/English edition.** Excellent, but licensed CC BY-SA-ND, which forbids the citation edits we need. Rejected.

**Decision.** Option A. Wording follows Heath; the only edits are inserted citations `[Post. 3]` etc. and modern punctuation. Explanatory commentary, where wanted, is clearly separated from the proof text.

**Consequences.**
- Proof text must be transcribed, not retyped from memory; AV-004 covers this.
- The Greek text toggle (candidate feature) would need a separate public-domain source (Heiberg).

**Reversal conditions.** Revisit if a reader audience finds Heath's register a barrier and a paraphrase layer (not replacement) is wanted.

### D-005 Documentation exemptions
**Decided:** 2026-10-29
**Recorded:** 2026-10-29
**Status:** Accepted
**Authors:** Shane Hartley (with Claude)
**Related:** README.md §Build requirements

**Context.** The project-scaffold standard requires Tier 1 omissions, and recommends Tier 2/3 omissions, be recorded.

**Decision.** The following are exempt:
- **`BUILD.md`** (Tier 2) — there is no build. The one-line local-serve command in README.md is the whole recipe. Revisit if D-001 is reversed.
- **`CLAIMS.md`** (Tier 3) — the project asserts nothing new about the world; Euclid's claims are Euclid's. Revisit if the project starts publishing its own results (e.g. a formal analysis of the I.1 intersection gap).
- **`VOCABULARY.md`**, **`SECURITY.md`**, **`BENCHMARKS.md`**, **`CITATION`** — no sibling project, no attack surface beyond a static site, no performance requirement, not intended for citation.
- **`TESTING.md`** — test strategy is two Node scripts; described in CLAUDE.md §Build & test. Revisit if a browser harness is added.
- **`CONTRIBUTING.md`** — solo project. Revisit on the first external PR.

All Tier 1 documents are present. `BUGS.md` and `IMPROVEMENTS.md` are adopted (in-repo tracking suits a solo, AI-partnered workflow).

**Consequences.** Lifecycle checklist items referencing exempt documents are themselves exempt for this project.

**Reversal conditions.** Per-document, as listed above.

### D-006 Numeric QED check with relative tolerance, not symbolic verification
**Decided:** 2026-10-29
**Recorded:** 2026-10-29
**Status:** Accepted
**Authors:** Shane Hartley (with Claude)
**Related:** F-003, AV-007, SPEC.md §Tolerance

**Context.** The site should show the proposition *holding*, not merely assert it. Two ways to do that.

**Options.**
- **A. Numeric evaluation of claims at the current drag position, with tolerance.** Cheap, live, honest about what it is (a demonstration, not a proof). Chosen.
- **B. Symbolic/formal verification (e.g. an embedded prover).** Out of proportion to the project and contradicts D-001's no-dependency stance. Rejected.

**Decision.** Option A. Claims are evaluated in floating point with the tolerance rule in SPEC.md; the readout labels the result as a numeric residual, never as "proved".

**Consequences.**
- The readout wording is "✓ holds · residual 0.000", not "proved".
- Near-degenerate drags can produce large relative residuals; AV-007 covers false fails.

**Reversal conditions.** Revisit if the project's scope grows to include its own mathematical claims (which would also lift the CLAIMS.md exemption in D-005).

### D-008 Intersection branches are chosen by rule, not by drag continuity
**Decided:** 2026-10-30
**Recorded:** 2026-10-30
**Status:** Accepted
**Authors:** Shane Hartley (with Claude)
**Related:** F-002, AV-003, SPEC.md §Branch selection

**Context.** Two-point intersections need a rule for which point the scene keeps. The original Phase 1 acceptance ("A dragged past B does not flip C") was ambiguous: with `pick: "ccw"`, dragging A straight through B reverses the direction AB, so the rule moves C to the other side of the screen. Whether that counts as a flip depends on whether the branch is defined relative to the construction or relative to the reader's drag history.

**Options.**
- **A. Rule-first.** The declared `pick` rule decides on every recompute; branch memory (nearest previous point) is used only when the configuration is within δ of tangency, where the rule is numerically unreliable. The figure is a function of the givens' positions alone. Chosen.
- **B. Continuity-first.** The rule seeds the initial choice; thereafter the scene keeps whichever candidate is nearest the previous value. Matches the old acceptance wording, but the figure becomes path-dependent and can place a point on the opposite side of a line from the one Heath's proof states. Rejected.

**Decision.** Option A. Heath fixes sides relative to lines ("on the same side", "on the other side of"), which is exactly what orientation-based `pick` rules encode, so the figure cannot contradict the proof text. In I.1, C is always on the positive-orientation side of directed AB; dragging A through B moves C to the other side of the screen, and that is correct behaviour.

**Consequences.**
- Same givens, same figure, regardless of drag path; the linter can test a static grid rather than replaying paths.
- AV-003 detection becomes an orientation-invariance check, not a screen-position check.
- Screen-relative picks (`"above"` etc.) remain available but are discouraged: they reintroduce genuine flips when the defining line passes vertical or horizontal. Each use should be justified in the data file's comments.
- Branch memory is a numerical safeguard near tangency only, not a behavioural feature.

**Reversal conditions.** Revisit if a proposition's figure is determined by something other than orientation relative to its defining objects and no `pick` rule can express it without path memory.

### D-009 Vendor web fonts; no third-party font requests
**Decided:** 2026-10-30
**Recorded:** 2026-10-30
**Status:** Accepted
**Authors:** Shane Hartley (with Claude)
**Related:** D-001, D-002, F-015, SPEC.md §Theme tokens

**Context.** The Instrument mock-up loads IBM Plex Mono and Barlow Condensed from Google Fonts. D-001 rules out runtime dependencies and expects any third-party asset to be vendored into `docs/`.

**Options.**
- **A. Vendor the woff2 files into `docs/fonts/`.** Both families are SIL Open Font License; works offline and on `file://`-adjacent local servers; no request to a third party per page view. Chosen.
- **B. Google Fonts `<link>`.** Nothing to commit, but an external dependency and a third-party request on every view. Rejected.

**Decision.** Option A. Only the weights the design uses are committed (Plex Mono 400/500/600, Barlow Condensed 500/600), Latin subset, with the OFL text alongside. `instrument.css` declares them with `@font-face` and `font-display: swap`.

**Consequences.**
- A few hundred KB of binary assets in the repo.
- Greek glyphs (candidate Greek text toggle) would need a wider subset or another family.

**Reversal conditions.** Revisit if the font files need frequent updating or the Greek toggle requires a family that cannot be vendored.

### D-010 Heath's proof is read through the step cards; no separate proof panel
**Decided:** 2026-10-30
**Recorded:** 2026-10-30
**Status:** Accepted
**Authors:** Shane Hartley (with Claude)
**Related:** D-002, D-003, D-004, F-005, F-007, SPEC.md §Proposition data

**Context.** The SPEC schema carried both `steps[].text` and a separate `proof` list, but the Instrument mock-up (D-002) has no proof panel: the only proof wording is in the step card. F-007 needs a place for Heath's text.

**Options.**
- **A. Step cards carry Heath's text.** Each step's `text` is the corresponding passage of Heath with inline citations; stepping through reads the whole proof. Keeps the Instrument layout unchanged. Chosen.
- **B. Separate proof panel or collapsible section.** Whole proof visible at once, but changes the agreed layout and duplicates text between steps and proof. Rejected.

**Decision.** Option A. The `proof` field is removed from the schema. Non-Heath commentary goes in an optional per-step `note`, rendered apart from the proof text.

**Consequences.**
- One copy of the proof text per proposition, so one place for AV-004 checking.
- Steps must be cut where Heath's text naturally divides; a step's construction and its justification may share a card.
- Long proofs (I.44–I.47) mean long step cards; the card must scroll gracefully.

**Reversal conditions.** Revisit if readers need the whole proof visible at once (e.g. for printing or the long propositions), in which case a read-only "full text" view assembled from the step texts is the first option to try.
